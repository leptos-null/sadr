# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Package manager is **bun** (`bun.lock` is the lockfile — don't use npm/yarn).

- `bun install` — install deps
- `bun run dev` — `wrangler dev`, local dev server on `http://localhost:8787`
- `bun run test` — full vitest suite (`@cloudflare/vitest-plugin`, runs in a real Miniflare Workers runtime, not plain Node)
  - single file: `bun run test test/gemini.spec.ts`
  - single test: `bun run test -t "test name"`
- `bun run typecheck` — typechecks `src/` and `test/` as two separate programs: `test/tsconfig.json` adds the `cloudflare:test` types, which the root config deliberately leaves out so `src/` can't typecheck against a test-only module. A plain `bunx tsc --noEmit` checks `src/` only.
- `bun run cf-typegen` — `wrangler types`; **re-run after any binding/secret change in `wrangler.jsonc`** to regenerate `worker-configuration.d.ts`
- `bun run deploy` — `wrangler deploy`

### Local dev gotchas

- Secrets (`DISCORD_TOKEN`, `GEMINI_API_KEY`) come from a git-ignored `.dev.vars` in the repo root, not `wrangler.jsonc`.
- Nothing auto-triggers the bot's Gateway connection in local dev. Hit `curl localhost:8787` once after starting `wrangler dev` to fire `ensureConnected()`. The cron (`scheduled` handler) doesn't run locally either — trigger it manually with `curl "http://localhost:8787/cdn-cgi/local/scheduled"` if you need to test the self-heal path.
- Running `wrangler dev` / `vitest` may need a local loopback listener that a process sandbox can block (`EPERM` on `listen`) — that's an environment restriction, not an app bug.
- Per Cloudflare's known issues, DO alarm methods (the primary keep-alive loop — see `discord-gateway.ts`'s `alarm()`) can silently fail after a hot reload in `wrangler dev` (i.e. after editing code while it's running). If the bot seems to stop reconnecting after a local code edit, restart `wrangler dev` before assuming it's an app bug.

### Cloudflare docs

`AGENTS.md` in this repo instructs: always fetch current Cloudflare docs before touching Workers/Durable Objects code, since platform APIs and limits change (e.g. this project's DO class lifecycle already moved from `migrations` to the newer `exports` field, and new DO namespaces now require the SQLite storage backend). Use the `cloudflare-docs` MCP server (configured in `.mcp.json`), not prior/training knowledge, for anything Workers/DO/KV/R2/D1/Queues/Vectorize/Workers AI/Agents-SDK related.

This project authenticates to the Gemini API with the `x-goog-api-key` header, per <https://ai.google.dev/api/generate-content#authentication>; the `?key=` query-param form shown in some other Gemini doc examples is not what this project uses.

## Architecture

sadr is a Discord bot that replies to `@mention`s in guild channels and to any message in a DM, using the Gemini API, running as a single Cloudflare Worker.

**Gateway connection, not Interactions webhooks.** The bot holds a persistent outbound WebSocket to Discord's Gateway rather than registering slash commands / an HTTP interactions endpoint. This is a deliberate choice (free-text mention chat needs the Gateway; Interactions only supports slash commands) — don't reach for slash commands without revisiting that decision.

**Structured JSON logging everywhere, not pre-formatted strings.** Every log call across the codebase — every `console.error`/`warn`/`log`, and every `debugLog()` factory (`src/log-level.ts`; returns `unknown`, not a string) — logs a structured object (`{ message: "...", ...fields }`) rather than a baked-in string, per Cloudflare's Workers Logs best practice: structured fields are individually filterable/aggregatable in the dashboard, where a pre-formatted string is only text-matchable. `log-level.ts` also exports `errorMessage()`: every `console.error({...}, error)` call site embeds `errorMessage(error)` as a string field inside the structured object *and* still passes the raw `error` object as a second argument, since Cloudflare's log capture doesn't reliably surface a caught `Error`'s own `.message` that way — only its stack frames — so dropping either half loses either the filterable message text or the stack trace. This was added after a real incident where an error's message was lost from production logs because it was passed only as a separate `console.error` argument.

- `src/index.ts` — the Worker entry. Re-exports the `DiscordGateway` Durable Object class (required for `wrangler.jsonc`'s `exports` binding) and defines `fetch`/`scheduled`. Both handlers just call `ensureConnected()` on the **one** singleton DO instance (`env.DISCORD_GATEWAY.getByName("default")`) — `fetch` is a health check that fires it via `ctx.waitUntil()` without blocking the response, `scheduled` (5-min cron) awaits it directly as a secondary self-heal in case the socket dropped (the DO's own alarm loop, below, is the primary keep-alive mechanism).
- `src/discord-gateway.ts` — the `DiscordGateway` DO. This is where almost all the bot logic lives: raw Discord Gateway protocol handling (HELLO → IDENTIFY/RESUME → heartbeat loop → dispatch events), session state (`sessionId`/`resumeGatewayUrl`/`sequence`/`botUserId`/`botUsername`) persisted to DO storage so a restart can RESUME instead of re-IDENTIFY, and the `MESSAGE_CREATE` → mention check → Gemini → Discord REST reply pipeline. Logs at each lifecycle step (connect, Hello, READY, close code/reason, mention handling) — check these first when the bot isn't responding.
  - The outbound socket is a plain `new WebSocket(url)` client connection. **Do not call `.accept()` on it** — that method is only valid on the server side of a `WebSocketPair()` (an inbound connection a Worker/DO accepts), and throws on a client-constructed socket.
  - **A self-rescheduling DO alarm (`alarm()`, every `KEEPALIVE_INTERVAL_MS` = 60s) is what actually keeps the bot connected long-term.** An outbound connection (our Gateway WebSocket) only keeps a Durable Object alive for a maximum of 15 minutes; after that, the DO is evicted — killing the socket — after just 70-140s with no incoming request/RPC/event. The 5-min `scheduled` cron alone is too infrequent to prevent that gap. `ensureConnected()` schedules the first alarm (and re-schedules one if it's ever found missing, e.g. after an unrelated eviction/restart) then delegates to a private `connectIfNeeded()`; `alarm()` calls that same `connectIfNeeded()` (not `ensureConnected()` — that would double-write the alarm) and unconditionally reschedules itself in a `finally`, regardless of whether the connection attempt succeeded.
  - Responds to guild messages that `@mention` the bot, and to any message in a DM (`isAddressedToBot()` in `src/discord/mentions.ts`, keyed off whether `guild_id` is present on the dispatch). Requests the privileged `MESSAGE_CONTENT` intent (must also be enabled under the bot's Privileged Gateway Intents in the Discord Developer Portal, or Discord rejects the connection with a non-resumable invalid session) — needed because without it, `content`/`embeds`/`attachments` come back empty for any message that doesn't mention the bot, isn't a DM, or wasn't sent by the bot, which is most of what `fetch_message_history`'s `around` fetch (see `src/gemini.ts` below) pulls in.
  - Bot identity (`botUserId`/`botUsername`) is resolved via REST (`getCurrentUser`, `GET /users/@me`) in `connectToGateway()` before the socket even opens, not solely from the Gateway's `READY` dispatch — a `RESUME` never re-sends `READY`, so a session that only ever resumes would otherwise never learn its own identity.
  - Verbose tracing (raw Gateway payloads, and — in `src/gemini.ts`/`src/discord/rest.ts` — raw Gemini and Discord REST request/response bodies) is gated behind `LOG_LEVEL="debug"` through the shared `debugLog()` helper in `src/log-level.ts` — set `LOG_LEVEL="debug"` in `.dev.vars` locally; never in production.
  - While a reply is being generated, a private `startTyping()` triggers Discord's typing indicator immediately and re-triggers it every `TYPING_REFRESH_MS` (8s) — comfortably under the ~10s Discord shows it for — until the returned stop callback runs in a `finally` around the `MESSAGE_CREATE` reply pipeline, regardless of success, failure, or fallback.
  - **`MESSAGE_CREATE` also resolves any Discord message-link URL in the trigger's content**, so the model can be told what a linked message actually says. It builds a `canReadLinkedChannel(channelId, userId)` callback (passed into `generateReply`, below) that runs a two-part check for each candidate link's channel: `canReadChannel` (can the asker themselves see it — `src/discord/permissions.ts`) and, for a guild reply, `isAtLeastAsReadableAs` (is it no narrower than the channel the reply is posted in — an asker with access to a private channel shouldn't be able to get the bot to repeat its contents somewhere everyone can see). `governingChannels` resolves a channel to the one whose overwrites actually govern it (itself, or — for a thread — its parent) plus that channel's category, since a thread carries no overwrites of its own. Two request-scoped caches (`channelCache`, `memberCache`, both keyed by the in-flight *promise* so concurrent callers can't race past an empty cache) mean multiple links into the same guild/channel in one trigger cost one REST round-trip each, not one per link.
- `src/discord/rest.ts` — Discord REST v10 calls (bot-token `Authorization` header) through a shared `discordFetch()` helper: fetching the Gateway WSS URL, the bot's own identity (`getCurrentUser`), posting a channel message (optionally as a reply via `message_reference`), triggering the typing indicator (`triggerTyping`), fetching channel messages around a given id (`getChannelMessages`, using Discord's `around` param — both earlier and later messages in one call), and fetching a channel's/guild's metadata and a guild/thread member's data (`getChannel`, `getGuild`, `getGuildMember`, `getThreadMember` — the last two feed the message-link permission check above; a 404 on either is treated as "not a member," via an `allowMissing` overload of `discordFetch` that returns `null` instead of throwing). `discordFetch()` also `console.warn`s (unconditionally, *not* `LOG_LEVEL`-gated, since it needs to be visible in production) whenever a call takes longer than 3s — added after a production incident where a `getGatewayBotUrl`/`getCurrentUser` call that should complete in milliseconds instead took minutes (the underlying cause was Durable Object eviction, not the REST call itself; see the alarm note above).
- `src/discord/mentions.ts` — pure helpers: whether a message mentions a given user id, whether a message should be treated as addressed to the bot (DM or mention). Message content is passed to Gemini unstripped, mention tokens included — the system instruction (see below) teaches the model to recognize its own `<@id>`/`<@!id>` token.
- `src/discord/message-links.ts` — `extractMessageLinks` parses `discord.com/channels/{guild|@me}/{channel}/{message}` URLs (and the `ptb.`/`canary.` subdomains, the legacy `discordapp.com` host) out of message content. The leading guild segment is captured nowhere — verified live that Discord doesn't validate it against the channel it precedes, so a permission check must use the *fetched channel's own* reported `guild_id`, never this segment.
- `src/discord/permissions.ts` — `canReadChannel` (can one member read a channel: `VIEW_CHANNEL` + `READ_MESSAGE_HISTORY`, resolved through Discord's real `@everyone` → role → member overwrite precedence) and `isAtLeastAsReadableAs` (audience-wide: does every member who can read a reference channel also read this one, compared by overwrite ids with zero extra REST calls). Both deliberately don't fetch guild-level role *permissions*, so there's no `ADMINISTRATOR` bypass modelled — an admin might be wrongly denied; that's the accepted, safe direction to be wrong in for a bot deciding whether to relay content, not the reverse.
- `src/discord/gateway-types.ts` — Gateway payload envelope and opcode types.
- `src/gemini.ts` — drives `gemini-3.5-flash-lite` as a small function-calling agent, not a single-turn prompt.
  - Every call forces a function call via `toolConfig.mode: "ANY"`; `send_reply` is itself the terminal tool call (not a separate structured-output step) — keeps the request *type* uniform for the whole loop. Both tools are offered on every call **except the final allowed one**, which withholds `fetch_message_history` (and adjusts the system instruction to match, without naming the withheld tool — the model never saw it declared since calls are stateless) so the model is forced to conclude instead of looping on fetches without ever answering. Added after a production incident (`Gemini exceeded 6 calls without calling send_reply`, from when `MAX_GEMINI_CALLS` was 6) left a user with no reply at all.
  - `fetch_message_history` fetches around a message id (Discord's `around`, not `before`-only paging) — doubles as "give me more context" and "show me what a `replyToId` reply-chain link points to." With `message_id` omitted it passes `around: null` through, which drops the param so Discord returns the channel's most recent messages — there's deliberately no synthesized default anchor.
  - No accumulated transcript: fetched messages merge into a `Map<id, HistoryMessage>` (dedupes automatically), and each call gets a *freshly rebuilt* turn from that map — the model's own past tool calls are never echoed back to it.
  - **The wire payload is multi-channel, not single-channel.** `generateReply(env, botUserId, botUsername, trigger, fetchGuild, fetchChannel, fetchAround, canReadLinkedChannel)` resolves any Discord message-link URL in `trigger`'s content (via `discord-gateway.ts`'s `canReadLinkedChannel`, above) into its own channel, and `buildContents` serializes everything as `{guild?, channels: {channelId: {name, topic, messages} | {inaccessible: true}}, trigger: {channelId, messageId}, users}` — `trigger` is a *pointer* into `channels`, not the full message. A channel that was denied by the permission check, or whose channel-info/message fetch failed, gets exactly `{inaccessible: true}` rather than being silently omitted, so the model can see it can't be read instead of repeatedly re-requesting it (the trigger's own channel is always exempt from this, regardless of any auxiliary fetch failure). `fetch_message_history` takes an optional `channel_id`, restricted to a channel already present in `channels`. The payload is unbounded — no size-based trimming; per-fetch limits (`SEED_FETCH_LIMIT` 50 for the trigger's own automatic seed fetch, `TOOL_FETCH_LIMIT` 20 for both a model-issued fetch and the reply-target seed fetch, a smaller unnamed limit for a link resolution) are what keep it bounded instead.
  - `buildSystemInstruction` builds the system instruction per call so the model can recognize its own past messages (`userId === botUserId`) and resolve mention tokens.
- `wrangler.jsonc` — uses the current `exports` field (not the legacy `migrations` array) to declare the `DiscordGateway` DO with the SQLite storage backend, and `secrets.required` to declare `DISCORD_TOKEN`/`GEMINI_API_KEY` (drives both `Env` typing and `wrangler deploy` validation).

Test coverage is unit-level only (mocked `fetch`, pure logic) for the REST/Gemini/mentions/message-links/permissions helpers and the health-check response; the actual Gateway handshake (IDENTIFY/heartbeat/RESUME) is verified live via `wrangler dev` rather than automated tests. The DO's keep-alive *alarm scheduling* (as opposed to the handshake) does have test coverage, in `test/discord-gateway.spec.ts`, using `cloudflare:test`'s `runInDurableObject`/`runDurableObjectAlarm` helpers to inspect/trigger the alarm directly without needing a live connection. The message-link permission-check *composition* inside `discord-gateway.ts`'s `MESSAGE_CREATE` closure (`governingChannels`, gate ordering, the private-thread branches) is untested even though the pure pieces underneath it are — a deliberate scope call, not an oversight.
